两轮不是对照组：向下是冷轮，要把没量过的消息由 `contain-intrinsic-size` 的估值高度换成实测高度
（列表高度 198386 → 346620 px）；向上是暖轮，对象已经量过。所以改前改后只比同向的两轮。

数字说明什么：0.4.16 在这台机器上滚完 600 条消息，帧间隔贴着 60 Hz 的 16.7 ms，没有被主线程卡住的长任务，

尖峰是个位数帧，不构成持续卡顿；一台 12 核机器上的无头浏览器本来也很难卡，别把这个数字当成「手机上一定顺」。

## 产物身份（为什么这里写构建时间）

`dist/` 不进版本控制，谁都能重建，而 `package.json` 的版本号在重建后可能不变——光看「v0.4.16」认不出一份产物。
2026-11-21 这天就发生过：本表在 18:17:51 那份 dist 上跑出来，18:27:01 另一份重建的 dist 覆盖了它
（改名「文件夹→分组」与安全区改动，本地库版本同时从 12 升到 13）。那天在 18:27 之后跑的同一探针，
形状相同（向下 2 条长任务 / 向上 0 条），但那份产物不是 0.4.16 基线，未计入本表。
以后引用这张表，先核对「构建于」这一行。


## 边界

无头 Chrome 的数字只证明「没退化」，不代表真机手感：
它是同一台机器、同一份产物、同一组参数下的纵向对照，能回答「这次改动让滚动更慢了吗」，
不能回答「在我的手机上滑起来顺不顺」——真机的手感要看设备 GPU、触控采样率与实际内核版本，
这三样这台无头浏览器都没有。涉及设备行为的结论仍按 `inferred` 记，等真机取证。
